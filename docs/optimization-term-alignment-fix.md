# 术语对齐修复：从 Rerank 全军覆没到精准命中

> 修复日期：2026-05-11
> 涉及模块：`bootstrap/.../rag/core/rewrite/QueryTermMappingService`、`user-question-rewrite.st`、`t_query_term_mapping` 表

---

## 1. 问题现象

用户提问"发票抬头是什么？公司税号是多少？"，其中子问题"公司税号是多少"在 Rerank 阶段**全军覆没**——12 个候选 chunk 经 Rerank 模型打分后全部低于 0.2 阈值，输出为 0 条，导致 LLM 无法回答税号相关信息。

```
Rerank 分数过滤完成，阈值：0.2，输入：6，输出：0    ← 子问题2（公司税号是多少）
后置处理器 Rerank 完成 - 输入: 12 个 Chunk, 输出: 0 个 Chunk, 变化: -12
```

---

## 2. 根因分析

### 2.1 直接原因：术语鸿沟

用户口语表达与知识库文档术语完全不一致：

| 用户表达 | 知识库文档用语 |
|---|---|
| 公司**税号** | **纳税人识别号**：91330108MA9A1B2C3X |
| 开户行 | 开户银行、账号 |
| 对公账户 | 开户银行、账号 |

知识库文档（`开票信息.md`，15 家公司）全文使用"纳税人识别号"这一正式术语，"税号"这个口语词**在文档中从未出现**。

### 2.2 术语映射表缺失

`t_query_term_mapping` 表中配置了 `发票 → 开票信息` 的映射，但**缺少 `税号 → 纳税人识别号` 等关键映射**。

术语归一化日志证实了这一点：
```
查询归一化：original='发票抬头是什么？公司税号是多少？', normalized='开票信息抬头是什么？公司税号是多少？'
                                                                      ↑ 已归一化       ↑ 没动
```

### 2.3 Embedding 容错但 Rerank 不容错

这是 RAG 系统中的一个核心认知：

- **Embedding（向量检索）**：sentence-level 语义编码，对术语错位有一定容忍度，能粗召回相关 chunk
- **Rerank（cross-encoder 精排）**：字面 + 语义双重比对，严格评估 query-doc 相关性，对术语不匹配非常敏感

```
向量检索阶段："公司税号" 还能和 "纳税人识别号 + 数字" 算"相关" → 召回 12 个 ✓
Rerank 阶段：  "公司税号" vs "纳税人识别号" → 字面零交集 → 全部 < 0.2 ✗
```

**教训：RAG 不是"知识库里有就一定能答"——术语对齐做好，整个管线效率有数量级提升；做不好，写得再全的知识库也是死的。**

### 2.4 次要原因：分块策略过粗

`开票信息.md`（258 行，15 家公司开票信息）被切成**只有 2 个 chunk**，每个 chunk 包含 7-8 家公司的混合信息。Rerank 面对"公司税号是多少"这种无主语的泛问，难以从混杂了多家公司信息的 chunk 中给出高分。

---

## 3. 修复方案

采用**双层防御**策略，精确映射 + LLM 泛化互补。

### 3.1 第一层：DB 术语映射（精确、稳定）

向 `t_query_term_mapping` 表插入 6 条 finance 域映射规则：

```sql
INSERT INTO t_query_term_mapping
  (id, domain, source_term, target_term, match_type, priority, enabled, remark, create_by, update_by, create_time, update_time, deleted)
VALUES
  ('9990000000000000001', 'finance', '统一社会信用代码', '纳税人识别号', 1, 70, 1, '口语 -> 正式术语', 'system', 'system', NOW(), NOW(), 0),
  ('9990000000000000002', 'finance', '统一信用代码',     '纳税人识别号', 1, 65, 1, '口语 -> 正式术语', 'system', 'system', NOW(), NOW(), 0),
  ('9990000000000000003', 'finance', '税号',             '纳税人识别号', 1, 60, 1, '口语 -> 正式术语', 'system', 'system', NOW(), NOW(), 0),
  ('9990000000000000004', 'finance', '对公账户',         '开户银行账号', 1, 55, 1, '口语 -> 正式术语', 'system', 'system', NOW(), NOW(), 0),
  ('9990000000000000005', 'finance', '对公账号',         '开户银行账号', 1, 55, 1, '口语 -> 正式术语', 'system', 'system', NOW(), NOW(), 0),
  ('9990000000000000006', 'finance', '开户行',           '开户银行',     1, 50, 1, '口语 -> 正式术语', 'system', 'system', NOW(), NOW(), 0);
```

插入后需清除 Redis 缓存（key: `ragent:query-term:mappings`）使其立即生效：

```bash
redis-cli -h 127.0.0.1 -p 16379 DEL "ragent:query-term:mappings"
```

**生效机制**：`QueryTermMappingService.normalize()` 按 priority 降序 + source_term 长度降序加载所有 `enabled=1, match_type=1` 的规则，串行对原文做替换。`QueryTermMappingUtil.applyMapping()` 有 `alreadyTarget` 检测防止重复替换。

### 3.2 第二层：LLM 查询改写术语扩展（泛化、自动）

修改 `user-question-rewrite.st` prompt，让 LLM 在改写阶段对关键词做同义术语扩展：

```
## 术语扩展
- 当用户使用口语词、简称、缩写、别称时，在不改变原意的前提下补充常见正式术语或同义词
- 扩展格式：保留原词，并在原词后用中文括号补充 1-3 个强相关等价词
  例如"税号（纳税人识别号、统一社会信用代码）"
```

**效果**：LLM 改写时同时保留口语词和正式词，query 里覆盖多种表达：

```
输入：  公司税号是多少？
改写：  公司纳税人识别号（税号、统一社会信用代码）是多少
```

### 3.3 两层机制的互补关系

```
用户问："公司税号是多少？"
   │
   ▼ ① DB 术语归一化（精确替换）
   "公司纳税人识别号是多少？"
   │
   ▼ ② LLM 改写+扩展（泛化补充）
   "公司纳税人识别号（税号、统一社会信用代码）是多少？"
   │
   ▼ ③ Embedding + Rerank
   query 同时包含：纳税人识别号 + 税号 + 统一社会信用代码
   无论文档用哪种表达都能命中
```

| 维度 | DB 术语映射 | LLM 术语扩展 |
|---|---|---|
| 维护成本 | 高（手工配） | 低（自动） |
| 泛化能力 | 弱 | 强 |
| 准确性 | 高（人工审核） | 中（依赖 LLM） |
| 性能 | 极快（hash 查表） | 慢（一次 LLM 调用） |
| 覆盖面 | 低 | 高 |

**最佳实践**：高频核心术语走 DB（精确、稳定），长尾术语靠 LLM 兜底。

## 5. 剩余问题与后续优化方向

### 5.1 分块策略过粗（优先级高）

`开票信息.md` 仍只有 2 个 chunk，每个包含 7-8 家公司信息。Rerank 只能从 6 个候选中选 2 个（33%），而如果按公司切分为 15 个独立 chunk，候选命中率会大幅提升。

**建议**：按 `---` 分隔符或 `### 标题` 切分，每家公司 1 chunk（共 15 个 chunk），使 Rerank 能精准定位。

### 5.2 意图识别对括号扩展的鲁棒性

带括号的 query（如 `开票信息抬头（发票抬头、开票抬头、开票名称）是什么`）会被送入意图分类器。当前实测 score=0.96（甚至比无括号时还略高），说明 LLM 对括号扩展的理解能力良好。但建议在 `intent-classifier.st` 中加一句提示：

```
> 用户问题中圆括号内的内容是同义词扩展，仅用于检索召回，分类时可忽略括号内容。
```

### 5.3 术语映射的潜在污染风险

现有映射 `保险 → 互联网保险系统`（priority=40）在用户问 HR 域的"五险一金保险"时会错误替换为"五险一金互联网保险系统"，产生噪声。建议：

- 短期：将此条 `enabled=0`，让 LLM 扩展兜底
- 长期：让 `QueryTermMappingService.normalize()` 支持上下文感知，只在 biz 域意图时才启用该映射

## 6. 关键学习点

1. **Rerank 是双刃剑**：精度高但对术语对齐很敏感。向量检索能容忍术语错位，rerank 模型更挑剔
2. **术语映射和 LLM 扩展要互补**：高频核心术语走 DB（精确），长尾术语靠 LLM（泛化），两者不冲突
3. **分块粒度直接影响 rerank 质量**：chunk 太大噪声多，rerank 信号被稀释；chunk 太小丢失上下文。需要按文档结构选择合适的分块策略
4. **Redis 缓存必须主动清除**：直接操作 DB 后需清 `ragent:query-term:mappings` 缓存 key，否则新规则不生效（TTL 7 天）
5. **Rerank minScore 阈值是全局一刀切**：`rag.search.rerank.min-score=0.2` 对所有问题统一生效，可考虑改为动态阈值或在输出为 0 时触发降级策略
